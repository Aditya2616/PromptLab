Prompt engineering as optimisation · mutate → score → select

Prompts, evolved against a score.

A population of prompt variants is mutated, scored on a dev split, and culled. The winners are then tested once on data the search never saw, next to a random-search baseline that got the same number of dev evaluations. Everything below replays real runs of this code on a small local model.

Read this before trusting a number

  • Much of the gain is output-format control. A 0.5B model often knows the answer but replies in a shape the scorer rejects. Telling it to reply with only the answer is worth many points; that is a real effect, but it is not reasoning.
  • Dev sets are noisy. At a couple of hundred items the dev score still has a standard error of several points, so some "improvements" during search are luck. That is why winners are re-scored on a separate test split.
  • The test split is touched once, after the search is finished. Dev minus test accuracy of the winner is the winner's-curse gap.
  • Random search at equal budget is the fair baseline: same operators, no selection feedback, the same number of dev evaluations. If evolution does not beat it, selection is not adding anything.
  • BoolQ has no headroom for a model this size: the majority answer already scores about as well as the first-draft prompt does (the numbers are in the tables above).
